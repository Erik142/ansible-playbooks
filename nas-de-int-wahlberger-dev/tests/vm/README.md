# Local VM fixture (qemu, Apple Silicon)

Automates the manual preparation in `inventories/vm/README.md`: a disposable
openSUSE Tumbleweed VM on a macOS arm64 host (qemu + HVF). Every `[V]`
scenario of the backup feature runs against it (T-27 to T-30). It is never
nas, cloud or pi, holds no real credential, and only the throwaway ssh key
generated by `up.sh` can log in.

## Use

```sh
cd nas-de-int-wahlberger-dev
export FIXTURE_VM_DIR=/some/dir/with/20GB-free   # default ~/.cache/nas-fixture-vm
tests/vm/up.sh                  # first run ~10-15 min (builds the image), later runs ~1 min
tests/vm/snapshot.sh clean      # named clean state (all 5 disks; reboots the guest once)
tests/vm/reset.sh clean         # roll everything back to it, VM running again in ~1 min
tests/vm/down.sh                # graceful poweroff, disks kept
tests/vm/down.sh --destroy      # also delete the disks (next up.sh starts fresh)
tests/vm/down.sh --purge        # additionally delete the cached images (re-downloads)
tests/vm/up.sh --reprovision    # rerun only the in-guest provisioning (idempotent)
```

```sh
ssh -i $FIXTURE_VM_DIR/id_fixture -p 2222 fixture@127.0.0.1
PATH=~/.pyenv/versions/ansible-bind9-venv/bin:$PATH \
  ansible -i inventories/vm -i tests/vm/inventory.yml nas -m ping
ansible-playbook -i inventories/vm -i tests/vm/inventory.yml backup_disk_init.yml ...
```

`tests/vm/inventory.yml` is a second inventory that only overrides the
host's connection variables (`127.0.0.1:2222`, the throwaway key); the fixture
`group_vars` still come from `inventories/vm`. Set the same `FIXTURE_VM_DIR`
for ansible as for `up.sh`. Port 8000 of the guest (restic) is forwarded to
`127.0.0.1:8000`.

Console log (serial): `$FIXTURE_VM_DIR/console.log`. Logs of the build and
provisioning: `build-root.log`, `provision.log` in the same directory.

## Running the backup scenarios (T-27 to T-30)

`tests/vm/ans.sh ansible-playbook ...` runs Ansible against the VM only (it refuses unless the
fixture host resolves to 127.0.0.1:2222, uses `tests/vm/ansible.cfg` so the 1Password vault script
is never called, and adds the production non-secret vars minus the fixture overrides).
`tests/vm/stack.sh` applies the roles of the backup stack. `tests/vm/scenarios/` holds one script
per group of scenarios (`t27-*` init/mount, `t28-*` btrbk/db_dump, `t29-*` rest-server and
maintenance, `t30-*` guards/reboot/flags/keys/README); each appends to
`$FIXTURE_VM_DIR/results.tsv`, and `make-results.py` renders `RESULTS.md`. Snapshots used:
`clean` (provisioned, nothing applied, backup disk blank) and `stack` (backup disk initialised,
stack applied, restic repository `cloud` initialised). Scenario helpers (`rcli` restic client,
`g.sh` / `b.sh` for ad-hoc guest commands) are in `scenarios/`. `RESULTS.md` has the outcome and
the defect log.

## What is provisioned

| Item | Value |
|---|---|
| OS | openSUSE Tumbleweed aarch64, kernel-default, btrfs root (`@`, plus `@/home`, `@/var`, `@/.snapshots`), systemd, firewalld (running), podman, snapper, sqlite3, polkit |
| User | `fixture`, key-only ssh, passwordless sudo, polkit-allowed (so `firewall-cmd --state` works unprivileged) |
| Disks (virtio-blk, serials) | `FIXTUREROOT` 20 GiB, `FIXTUREDATA` 10 GiB, `FIXTURECONTAINERS` 10 GiB, `FIXTUREBACKUP` exactly 21474836480 bytes and blank, `FIXTURESCRATCH` 10 GiB and blank |
| By-id | `/dev/disk/by-id/virtio-FIXTUREBACKUP` (= `backup_disk_device`) |
| `/mnt/data`, `/mnt/containers` | btrfs with the fixture UUIDs `...0d1` / `...0c1`, subvolumes `@data` / `@containers`, fstab entries as in `storage_mounts` |
| snapper | configs `data`, `containers` |
| Postgres | rootful podman container `fixture-postgres` (postgres:16, `--restart=always`, data in `/mnt/containers/fixture-postgres`), db/user `fixture`, table `t` |
| SQLite | `/mnt/containers/forgejo/volume/data/forgejo.db` |
| Podman network | `ac45-allowed`, 10.89.45.0/24 |
| Network | qemu user-mode NAT, subnet 192.168.122.0/24 (so `restic_server_allowed_sources` matches; host-forwarded connections arrive from 192.168.122.2), guest 192.168.122.50, ssh on 127.0.0.1:2222 |
| sysctl | `net.ipv4.ip_forward=1` (as production, see the Podman ip_forward note) |

Snapshots are qcow2 internal snapshots of all five disks, taken with the guest
cleanly powered off (not `savevm`: HVF on aarch64 does not support live VM
state save). The UEFI variable store is not part of the snapshot.

## Deviations from the manual README and from production

- **Image is built, not downloaded.** openSUSE publishes no Tumbleweed aarch64
  cloud/JeOS image (the `ports/aarch64/tumbleweed/appliances` directory holds
  only 32-bit ARM images). `up.sh` therefore downloads the sha256-verified
  Leap 16.0 Minimal-VM aarch64 Cloud image, boots it once purely as a
  bootstrap host, and installs Tumbleweed from the aarch64 ports repositories
  onto a blank disk with `zypper --root` (`build-root.sh`: GPT, ESP + btrfs,
  grub2-arm64-efi). Leap's own root is xfs, which is why it is not used as the
  guest. The built `tw-base.qcow2` is cached; delete it to rebuild.
- No cloud-init in the final guest; the throwaway key and sudoers are baked in.
- `selinux=0` on the kernel command line (the chroot-built tree is unlabelled).
- Root btrfs layout is simplified (no Tumbleweed snapshot-rollback layout, no
  snapper `root` config, no rebootmgr/transactional-update).
- SSH is on port 2222 of localhost, so `ansible_host`/`ansible_port` are
  overridden by `tests/vm/inventory.yml`, not by editing `inventories/vm`.

## What the aarch64 guest does and does not prove

Proves: the playbooks' logic on a real Tumbleweed userland with real btrfs,
block devices addressed by `/dev/disk/by-id`, systemd units and timers,
firewalld, rootful Podman Quadlets and snapper; formatting guards (size,
serial, blank-disk checks); idempotency; failure and alert paths.

Does not prove:

- **x86_64 production.** The guest is aarch64, the NAS is x86_64. Container
  images must be multi-arch (`restic/rest-server`, `postgres` are). The OBS
  `filesystems` repo (btrbk) must carry an aarch64 build; package versions can
  differ from what the NAS has. Anything arch-specific (QuickSync/OpenVINO for
  Immich, x86-only images) cannot be tested here.
- Real hardware: the 6 TB HDD, SMART data (`smartd` sees virtual disks), spin-up,
  timings, the real disk's by-id/WWN path format (`wwn-0x...` vs `virtio-...`).
- Real network: user-mode NAT stands in for the home LAN and ZeroTier; the
  source CIDRs of production (10.10.0.0/16, 10.243.0.0/16) are not exercised,
  only the fixture's CIDRs.
- Anything depending on the kernel/btrfs-progs versions of the actual NAS
  rather than current Tumbleweed aarch64.
